# 前后端通信

> 讲"两边怎么说话"。数据字段定义在 [contract.md](contract.md)，不在这里重复。

---

## 1. 通道

| 用途 | 方式 |
| --- | --- |
| **主通道**：数据请求、命令、将来的实时推送 | **一条 WebSocket 长连接** |
| 加载页面、静态资源 | HTTP（一次性） |

**不使用轮询。**

**为什么选 WebSocket**：将来的实时功能需要**服务端主动推数据**，HTTP 做不到（只能轮询，延迟与负载都差）。
现在用 WebSocket，等于顺手把实时的地基打好，不额外花成本。

> 对标：Chrome DevTools Protocol 用单条 WebSocket 承载全部命令；Jupyter 用 HTTP 管管理、WebSocket 管数据通道。
> 共同模式是——**低频请求–响应走 HTTP，高频与推送走长连接**。

## 2. 消息信封

```json
{ "id": 42, "type": "query_range", "payload": { } }
```

| 字段 | 说明 |
| --- | --- |
| `id` | 请求编号。**有 `id` = 请求**，后端必须回同 `id` 的响应 |
| `type` | 消息类型，集中登记 |
| `payload` | 消息内容 |

**无 `id` 的消息** = 服务端主动事件或推送（将来的实时数据走这里）。

统一信封的价值：请求–响应与主动推送**共用一条链路、一套解析代码**。

## 4. 请求风暴（**本节是本模块最容易踩的坑**）

连续缩放或拖拽时，前端可能每秒发出几十次数据请求。不处理会导致后端堆积、响应回来时数据早已过期，
**交互反而更卡**。

**两条一起用**：

| 手段 | 做法 |
| --- | --- |
| **① 按帧节流** | 在 `requestAnimationFrame` 里发请求，**每帧最多一次**。不要在每个 `mousemove` / `wheel` 事件里直接发 |
| **② 代次作废** | 请求带单调递增的代次号；响应回来时若已有更新的请求发出，**直接丢弃旧响应** |

可选优化：后端收到新请求时中止上一个正在计算的聚合。

> **必须配可运行的示例代码**（放 [guides/ai-coding-rules.md](guides/ai-coding-rules.md)）。
> 否则极容易被实现成"每个 mousemove 发一次请求"——那是本项目最典型的性能塌方点。

---

## 5. 大数据块

按聚合分层的设计（见 [ARCHITECTURE.md](ARCHITECTURE.md) §2），单次响应约等于**画布像素宽度个 min/max 对**（约 2000 条），JSON 完全够用。

若将来真出现大块数据：WebSocket **原生支持二进制帧**，可切紧凑编码。
**先不做**——等对标实验测出真实体量再决定，避免过早优化。
