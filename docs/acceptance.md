## 1. 编号体系

文档里到处在用 `S5`、`D3`、`U1` 这类编号。**编号必须有唯一的登记处**，
否则换一个会话或换一个模型后，读到 `S5` 无从解析——引用的内容等于不存在。

**新增前缀必须先登记到本表**，否则 `check_docs.py` 会拒绝提交。

| 前缀 | 含义 | 定义位置 | 有效范围 |
| --- | --- | --- | --- |
| `G` | 项目目标 | 本文件 §2 | G1–G5 |
| `S` | 成功标准 | 本文件 §3 | S1–S7 |
| `F` | 功能范围 | 本文件 §4 | F1–F3 |
| `SC` | 使用场景 | 本文件 §5 | SC1–SC7 |
| `D` | 架构决策 | [DECISIONS.md](DECISIONS.md) | D1–D12 |
| `U` | UI 层约束 | [ARCHITECTURE.md](ARCHITECTURE.md) §5 | U1–U6 |
| `M` | 前后端消息 | [messages.md](messages.md) | M1–M17 |
| `L` | 实时功能的待定问题 | [roadmap.md](roadmap.md) §3.2 | L1–L6 |
| `C` | 通信模块的待办项 | [protocol.md](protocol.md) §6 | C1–C4 |
| `T` | 框架自测项 | [guides/framework-test.md](guides/framework-test.md) §4 | T1–T8 |

**两条约定**：

1. 引用编号时写**完整前缀**（`S5`，不写"第 5 条"）。范围区间用顿号分隔的编号写法，不写 `S1~S7` 之外的变体。
2. 前缀是**全局**的。`U` 已被"UI 层约束"占用，所以使用场景改用 `SC`（Scenario），
   不能再用 `U`——同一前缀两套含义，等于两套都无法解析。

**检查规则**：`scripts/check_docs.py` 会扫描 `docs/` 下所有 markdown，
引用了登记范围之外的编号就拒绝提交。**围栏代码块内的内容不检查**——
那里写的是示例与验证证据，不是引用。

## 2. 目标

| 编号 | 目标 |
| --- | --- |
| G1 | 建立一个应用，覆盖嵌入式传感器数据的**提取 → 处理 → 可视化**链 |
| G2 | 扩展成本降为"**新增文件**"，而不是"修改核心 + 重新生成" |
| G3 | 文档自洽完备，使**新会话的 AI 只读文档即可继续开发** |
| G4 | 后续功能按同一套机制增量接入，**不为尚不存在的功能预留抽象** |
| G5 | 交付形态可打包为单个 exe；打包只发生在交付环节，**不得进入开发与调试流程** |

> G2 与 G3 是本项目区别于"一次性脚本"的全部理由。其余目标是它们的推论。

## 3. 成功标准

**每条都可验证。不接受"感觉上做到了"这类判断。**

| 编号 | 标准 | 验证方式 |
| --- | --- | --- |
| **S1** | 接入一个新的日志数据源，只**新增**文件，核心代码改动 **0 处** | 统计核心目录的 diff |
| **S2** | 新增一种绘图样式 / 换一套渲染内核 / 新增一种滤波算法，只**新增**文件，核心代码改动 **0 处** | 同上 |
| **S3** | 在**全新 AI 会话**中、不提供任何额外解释，仅凭仓库文档完成 S1 或 S2 | 实际跑一次，记录卡点并回补文档 |
| **S4** | 插件缺失或抛异常时，应用仍能启动并给出可读提示，**不崩溃** | 删除 / 损坏插件目录后启动 |
| **S5** | 从"插件文件放进目录"到"界面上能用"，中间**没有任何手工编辑文件或写代码的步骤** | 见 [ARCHITECTURE.md](ARCHITECTURE.md) §6.4 |
| **S6** | 数据源声明一个核心不认识的 `kind` 时，界面能正常显示并明确标注降级，**不崩溃** | 构造一个未知类型的插件试跑（[contract.md](contract.md) §4.2） |
| **S7** | **打包成 exe 后，插件目录仍可新增脚本并生效** | 打包后放一个新插件试跑 |

> **S3、S5、S7 是核心验收项。**
>
> 它们三个分别对应这个项目最容易被放弃的三件事：
> S3 —— 换会话后还能不能干下去；S5 —— 扩展要不要手工步骤；S7 —— 打包会不会把插件机制做废。
> 其余标准没做到只是功能缺失，这三条没做到则是**做这件事的理由不成立**。

## 4. 功能范围

本期的三个功能域。各自的模块、接口与硬规则在对应的模块文档里，本表只划边界。

| 编号 | 功能域 | 范围 | 模块文档 |
| --- | --- | --- | --- |
| **F1** | **数据源** | 任意格式日志 → 契约数据。两种模式：一次性（本期实现）、持续（预留接口） | [modules/source.md](modules/source.md) |
| **F2** | **数据绘制** | 绘制数据 → 画布。绘制方式本身是可变点，**不锁定任何绘图库** | [modules/renderer.md](modules/renderer.md) |
| **F3** | **数据滤波** | 全量数据 → 全量数据。可组合的处理链，可逐级开关 | [modules/filter.md](modules/filter.md) |

**F3 的硬约束**：滤波作用于**全量数据**，顺序在聚合之前。
若前端先聚合再滤波，滤波就是在聚合后的数据上做的——**结果直接是错的，不是慢**。
详见 [ARCHITECTURE.md](ARCHITECTURE.md) §2.4。

## 5. 使用场景

> 前缀是 `SC`，不是 `U`——`U` 已被 UI 层约束占用，见 §1。

| 编号 | 场景 |
| --- | --- |
| SC1 | 手头有一份设备日志，希望几分钟内看到曲线 |
| SC2 | 数据毛刺多，想套一层滤波再看 |
| SC3 | 内置图形不满足，让 AI 写一个新样式 |
| SC4 | 换了设备，日志格式变了，让 AI 写一个新数据源插件 |
| SC5 | 需要换一种更适配当前数据的绘制方式（渲染内核级替换） |
| SC6 | 数据里有偶发的单点尖峰，**必须能在图上找到它** |
| SC7 | 同一份数据想换一种存储格式，或手头拿到的是别人给的另一种格式 |

**主要使用者**：嵌入式开发者，熟悉 C，对其它编程语言与开源框架不熟悉。

由此推出两条硬约束：

1. **扩展面必须极窄且声明式**。不要求使用者读懂核心实现，也不要求他掌握核心所用语言。
   他做的事只有：把日志丢进来 → 在界面上选插件 → 让 AI 写新插件。
2. **扩展面即产品接口**。脚本语言、脚本加载机制、插件声明格式属于一等接口，必须在设计阶段定下来。

> SC6 是显示策略（禁止抽样）的来源：尖峰就是问题本身，抽样会把它抹掉。

## 6. 验收清单（Definition of Done）

**全部勾上才算本期完成。** 括号里是关联的成功标准或决策编号。

### 契约与校验

- [ ] 契约中不认识的字段在读写往返后**原样保留**
- [x] 校验器能拒绝一份错误数据并**定位到出错字段**
- [x] 校验器可**被自动化调用**（供测试与插件自检）

### 数据源

- [ ] 用一份真实日志，通过新写的数据源插件得到**合规数据**
- [ ] 载入该数据，**无需改代码**即可绘图
- [ ] 新增第二类数据源，核心代码**零改动**（S1）
- [ ] 数据源声明未知 `kind` 时，界面正常显示并标注降级（S6）

### 绘制

- [ ] 折线图与柱状图均可正常渲染，且**经同一接口接入**
      （验证方式：删掉内置实现后核心不报错，只是少一个选项）
- [ ] 缩放、平移、点标记、区间标记可用且流畅
- [ ] 在 100 万点的数据上，全览时**一个已知的单点尖峰仍然可见**（[ARCHITECTURE.md](ARCHITECTURE.md) §4）
- [ ] 界面明确标注当前是否处于**聚合显示状态**
- [ ] 渲染接口的数据入口支持**追加**，即使本期只调用一次
- [ ] 新增一个渲染样式插件，核心代码零改动，且**作者无需阅读核心代码**（S2）

### 滤波与聚合

- [ ] 至少一个滤波插件可挂载、可开关、**参数可在界面调节**（界面待第 5 批）
- [x] 滤波在聚合**之前**执行，且作用于**全量数据**

### 分层

- [x] **跨进程接口不存在"请求全量数据"的能力**——前端在结构上无法绕过分层
- [x] 数据量小于像素宽度时后端直接返回原始点，**前端代码路径不变**（前端只按 `aggregated` 换画法）
- [ ] 响应中带"本次是否聚合"标志，界面据此标注（标志与界面均已实现，待人工在浏览器确认）

### 存储

- [ ] 存储接口按"**按 x 范围读取**"定义，接口名里**不含格式名**
- [ ] JSON 实现与接口形状一致

### 插件机制

- [ ] 从插件文件放进目录到界面可用，**无任何手工编辑文件步骤**（S5）
- [ ] 删除或损坏插件目录后，应用仍能启动并提示原因（S4）
- [ ] 界面文案集中在文案表，逻辑代码中**无硬编码文案**

### 交付

- [ ] **开发流程中不存在"必须打包才能验证"的步骤**
- [ ] **打包成 exe 后，往插件目录放一个新插件仍能生效**（S7）

### 最终验收

- [ ] 在**全新 AI 会话**中，仅凭仓库文档完成一次插件接入（S3）
