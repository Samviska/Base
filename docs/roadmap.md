## 3. 未实现功能：实时数据更新

**状态**：需求已确认，本期不做。**将以"持续模式数据源插件"的形式接入，核心不需要改动。**

### 3.1 与静态分析的差别

| | 静态分析（本期） | 实时更新 |
| --- | --- | --- |
| 数据来源 | 一个已存在的完整文件 | 持续到来的数据流 |
| 数据状态 | 一次全量已知 | 不断增加 |
| 关键能力 | 缩放、平移、全览找极值 | 追加数据、自动滚动、**接收不丢数据** |
| 最易出问题处 | 格式解析 | **接收被绘制拖慢 → 丢数据** |

### 3.2 需要先决定的事

| 编号 | 问题 | 重要性 |
| --- | --- | --- |
| **L1** | 数据从哪里来（串口 / SEGGER RTT / 网络 / 正在增长的文件） | **最大的分叉，没有通用解** |
| **L2** | 速率：每秒多少点，峰值多少 | 决定缓冲与刷新策略 |
| L3 | 只显示最近 N 秒的滚动窗口，还是从头累积 | 决定内存与渲染策略 |
| L4 | 实时看的同时要不要同时存盘供事后细查 | 建议要，代价小 |
| L5 | 接收跟不上时：丢弃还是缓冲；丢弃了多少必须能报告 | **静默丢数据会导致错误结论** |
| L6 | 用设备自带时标，还是用接收时刻 | 决定 x 轴含义 |

> L1、L2 没有答案就无法开始设计。

### 3.3 系统必须具备的能力

1. **接收与绘制必须分离**（生产者–消费者）。接收循环只做"读进来、存下来"，绘制按固定节奏取数据。
   若在同一循环里，绘制一卡接收就停，数据丢了都不知道。
2. **缓冲与批量刷新**：数据到达速率与屏幕刷新率无关，中间必须有缓冲。
3. **丢数据必须可见**：缓冲区满而丢弃时，必须记录并显示"丢失了哪一段"。屏幕上出现一段平线时，必须能区分"设备没输出"还是"程序丢了数据"。
4. **显示策略不变**：仍用像素列 min/max，不得抽样。
5. **时间基准**：用设备上报时标或接收时刻；仍复用契约的数值毫秒表示。

### 3.4 本期已预留的位置

| 位置 | 现在的写法 | 写错的后果 |
| --- | --- | --- |
| 渲染接口的数据入口 | 设计成**可追加**（`appendData`），即使本期只调用一次 | 若写成"一次性传入全量数据"，将来做实时要改**所有**渲染器（含第三方插件） |
| 数据源接口 | 显式区分"一次性"与"持续"两种模式，本期只实现前者 | 若只按"读文件"设计，将来要动核心，甚至被迫新增插件类别 |

> 附带好处：静态加载文件 = 把全部数据"追加"一次，两条路径共用同一套渲染代码。

### 3.5 实施顺序

**先在静态分析上把契约、渲染接口、显示策略跑通，再做实时。**

理由：实时 = 静态 + 换数据源 + 渲染加追加。若静态部分未定型就做实时，两部分会同时返工；
而且实时调试难度远高于静态（数据不等人，无法反复重放）。
