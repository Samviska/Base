# 框架自测

> **测的不是功能，是"换一个会话、换一个模型之后，这套文档与规则还能不能干活"。**
> 这是验收（[acceptance.md](../acceptance.md) 的 S3），不是开发。
> **目标是找出洞，不是把测试跑绿。**

---

## 1. 适用场景

| 什么时候用 |
| --- |
| 更换 LLM 或更换工具（DSH / Claude Code / 其它）之后 |
| 怀疑文档失效、规则没被遵守时 |
| 定期验收，每隔一段时间做一次 |
| **新会话的第一件事**：确认自己有没有被"喂"到该有的规则 |

---

## 2. 前置条件

| 项 | 要求 |
| --- | --- |
| 会话 | **全新**，不带历史上下文 |
| 工作目录 | **项目根**（靠 `.git` 识别）。在父目录开会话，根 `AGENTS.md` 不会被注入 |
| 环境 | 已跑过 `python scripts/setup.py`（建 `.venv` + 装依赖 + 启用钩子） |
| 启动方式 | 第一条消息只说：`读 docs/guides/framework-test.md 并按其执行` |

**为什么开场白要这么短**：T1 测的就是"不靠额外解释能不能接上"。
提示给得越多，测出来的结果越不可信。

---

## 3. 安全边界（**先读这一节再动手**）

| 禁止 | 原因 |
| --- | --- |
| `git reset --hard` | 会丢掉**尚未提交**的改动 |
| `git checkout -- .`、`git clean -fdx`、`git stash drop` | 同上 |

> **这不是假想风险**：本项目建立这套机制时，一个测试脚本用了 `git reset --hard` 恢复现场，
> 结果把当轮**尚未提交的全部修复**冲掉了（连 `git add` 过的新文件一起），只能重做一遍。
> 教训记在 [DEVLOG.md](../DEVLOG.md) 里。

**规则**：

1. 临时文件统一加前缀 `_probe_`，测完**立即删除**。
2. 每完成一项，确认 `git status` 没留下意外改动。
3. 发现框架有洞时，**不要当场改框架**——测试与修复分成两次提交，
   否则回退时分不清"测试"和"修改"。
4. 状态不清楚就**停下来问**，不要猜着重置。

---

## 4. 测试项

### 4.1 只读项（不改动仓库）

做法：**先不看任何文件**，凭会话开始时就已有的信息作答；然后去查文档，对照。

| 编号 | 问题 | 通过判据（答案必须包含） |
| --- | --- | --- |
| **T1** | 开工前该按什么顺序读哪些文档？ | `overview.md` → `MODULES.md` → `modules/<模块>.md` → 按需 `contract.md` / `messages.md`；并知道**根 `AGENTS.md` 是自动加载的** |
| **T2** | 要新增一个数据源插件，改哪些文件？受什么约束？ | 位置 `plugins/sources/<名字>/`；需要**实现文件 + manifest**；只能依赖契约，**不得依赖核心内部 / 其它插件 / 界面**；必须**自校验输出**并指出出错字段路径；必须**声明 x 轴描述**；新增插件**不需要改核心** |
| **T3** | `S5`、`D3`、`U1`、`M6`、`C2` 分别是什么？ | 全部答对，并能说出定义在哪份文件（`acceptance.md` §1 是编号登记表） |
| **T4** | 滤波与聚合的执行顺序？为什么不能反？ | 顺序是**提取 → 滤波 → 聚合**；滤波必须作用于**全量数据**；顺序反了**结果是错的**（不是慢，是错） |

**T1 失败的含义**：根 `AGENTS.md` 没被自动注入（换工具了），或该文件写得太隐晦。
**T2 失败的含义**：模块文档或 `MODULES.md` 的导航断了。
**T3 失败的含义**：新会话不知道存在编号体系——`acceptance.md` 没被找到。
**T4 失败的含义**：`ARCHITECTURE.md` §2.4 没被读到，这是**最容易造成错误结果**的一条规则。

### 4.2 检查项（用一个临时探针文件）

新建 `docs/_probe_check.md`，内容按下面的表构造，然后跑 `python scripts/check_docs.py`。

| 编号 | 探针文件里放什么 | 期望结果 |
| --- | --- | --- |
| **T5** | 一个指向**不存在文件**的相对链接 | 报 **断链** |
| **T5** | 正文里写一个**超出登记范围**的编号（按 `acceptance.md` §1 的某段范围，故意越界） | 报 **引用了未定义的编号** |
| **T5** | 把同样的越界编号放进**围栏代码块**里 | **不报**（代码块内是示例与证据，不是引用） |

测完删掉探针文件，再跑一次确认恢复干净。

**T5 失败的含义**：链接与编号检查失效，或误报（误报会逼着人绕开规则，比不检查更糟）。

### 4.3 提交项（会真实改动仓库，可回滚）

**T6 — 违规提交必须被拦**

1. 新建 `backend/_probe_violation.py`（任意一行内容），`git add`。
2. **不用** `commit.py`，直接 `git commit -m "test"`。
3. **期望：被拒绝，退出码非 0**，理由包含「DEVLOG 未更新」与「VERSION 未更新」。
4. 删掉探针文件。

**T6 失败的含义**：`git` 钩子没启用或已失效——**所有提交前检查都静默失效了**，这是最危险的一种失败。

**T7 — 合规提交必须走通**

1. 把本次自测的结论追加到 `docs/DEVLOG.md` 最上面（格式见该文件顶部）。
2. `python scripts/commit.py -m "验收: 框架自测 T1–T8"` —— 用**系统 python** 启动，
   它应当自己切到 `.venv` 里的解释器。
3. **期望：提交成功**，`VERSION` 递增，提交信息形如 `vX.Y.Z 验收: ...`。

**T7 失败的含义**：日常提交流程断了，后续所有工作都做不下去。

**T8 — 钩子缺失必须被自检发现**

1. 把 `.githooks/pre-commit` 临时改名为 `pre-commit.bak`（**不要删除**）。
2. 跑 `python scripts/commit.py -m "test"`。
3. **期望：报错并给出恢复命令**，退出码非 0。
4. **必须恢复**：把 `pre-commit.bak` 改回 `pre-commit`，再跑一次 `check_docs.py` 确认正常。

**T8 失败的含义**：「配置指向正确、目标文件却没了」这种情况不会被发现，
提交检查静默失效——这正是当初复测找出的第 8 个漏洞。

## 5. 判定与记录

**全部通过**：在 `docs/DEVLOG.md` 记一条，写明做了哪几项、结论。

**有失败**：**不要当场改框架**。按下表记录后交给使用者决定：

| 项 | 内容 |
| --- | --- |
| 编号 | 哪一项（T1–T8） |
| 做了什么 | 可复现的最小步骤 |
| 实际结果 | 原样的报错或行为 |
| 期望结果 | 应该是什么 |
| 影响 | 这一项失效会导致什么后果 |

**结束前必须确认**：

```powershell
git status -sb                          # 工作区应干净、与远端一致
.venv\Scripts\python.exe scripts\check_docs.py   # 应输出「文档与契约检查通过」
Test-Path docs\_probe_check.md          # 应为 False
Test-Path backend\_probe_violation.py   # 应为 False
Test-Path .githooks\pre-commit.bak      # 应为 False
```

## 6. 常见错误

| 现象 | 原因 | 纠正 |
| --- | --- | --- |
| 会话开始就不知道该读什么 | 会话**不在项目根**打开，或工具不支持 `AGENTS.md` 约定 | 换到项目根重开会话；否则第一条消息让它先读 `AGENTS.md` |
| `commit.py` 报「暂存区为空」 | 它只提交**已 `git add`** 的内容 | 先 `git add`，再运行 |
| `check_docs.py` 报缺少 `jsonschema` | 用了系统 python，依赖装在 `.venv` 里 | 用 `.venv\Scripts\python.exe`，或确认 `commit.py` 会自动切换 |
| 报错里中文是乱码 | 控制台按 GBK 解码 UTF-8 | 脚本已重配置为 UTF-8；若仍乱码，检查是否用了旧版脚本 |
| 编号检查报"引用了未定义的编号" | 在**正文**里写了越界编号 | 把越界编号放进围栏代码块；或登记该前缀后更新范围 |
| 提交时提示勾子未启用 | 新 clone 的仓库，`core.hooksPath` 是本地配置、不随仓库分发 | 跑 `python scripts/setup.py` |

## 7. 已知边界（**当前检查覆盖不到的地方**）

诚实列出，避免误以为"检查通过 = 文档没错"：

| 边界 | 说明 |
| --- | --- |
| **未登记前缀查不出来** | 检查只校验**已登记**的前缀（见 `acceptance.md` §1）。若有人在正文里用了一个全新前缀（如 `X9`），不会被发现——因为要区分它与 `UTF8` 这类普通词会大量误报。新前缀靠**人工登记** |
| 合并提交不展开差异 | `--commit` 模式下过程约束会跳过 |
| CI 只检查最后一个提交 | 一次推送多个提交时，中间提交可能漏检 |
| 检查只管形式 | 能拦住"没写文档"，拦不住"文档写得含糊" |
