# 全局架构

> 本文档讲**整体怎么分层、什么不能越界**。单个模块的规则在 `modules/` 下。
> 数据字段定义在 [contract.md](contract.md)，不在本文档重复。

---

## 1. 分层与依赖方向

```
应用核心（稳定，很少改动）
      ↓ 只依赖
   数据契约（冻结，带版本）
      ↑ 只依赖
   插件层（可变，持续增长）
```

**依赖方向单向**：插件可以依赖契约，**不得**依赖核心内部实现。
核心只认识契约，**不认识**任何具体插件。

完整依赖图与三条硬规则，见 [MODULES.md](MODULES.md)。

## 2. 数据流

```
原始日志
  ↓ ① 数据源提取
契约数据（全量）
  ↓ ② 滤波链
滤波后数据（全量）
  ↓ ③ 聚合（按视口范围 + 目标分辨率）
绘制数据（≈ 像素宽度个 min/max 对）
  ↓ ④ 渲染
画布图形
```

**①②③ 全部在后端，④ 在前端。**

### 2.1 分层纪律：前端永远拿不到全量数据

靠**接口里没有那个选项**来保证，而不是靠约定：

| 接口 | 位置 | 暴露的能力 |
| --- | --- | --- |
| 后端内部数据接口 | 后端内部 | 读全量、按 x 范围读、写入、注解读写 |
| **前后端接口** | 跨进程 | **只有一样**：按「视口范围 + 目标分辨率」请求绘制数据 |

后者是前者的**受限视图**，因此前端**在结构上无法**绕过分层。

### 2.2 聚合的统一入口

- 前端请求：范围 + 目标分辨率（通常是画布像素宽度）
- 后端判断该范围内点数是否超过分辨率：
  - 未超过 → 直接返回原始点
  - 超过 → 返回像素列 min/max 聚合结果
- 响应带一个标志，说明本次是否发生聚合（供界面标注）

好处：**前端只有一条代码路径**，数据量大小都不改代码。

### 2.3 后端的缓存层次

| 层 | 缓存内容 | 失效条件 |
| --- | --- | --- |
| 提取结果 | 契约数据（全量） | 换输入文件 / 换数据源插件 |
| 滤波结果 | 滤波后的全量数据 | 滤波链或参数变化 |
| 聚合结果 | 某（范围, 分辨率）的绘制数据 | 视口变化 |

规则：**失效单向**（上层变化导致下层失效，反向不成立）。
**禁止跨层缓存**——例如前端缓存全量原始点，那就等于绕过了分层。

> 注意边界：前端**可以**缓存它**有权获得**的数据（聚合结果），以降低请求频率；
> 不可以缓存它**无权获得**的数据（全量原始点）。

### 2.4 为什么顺序不能颠倒

[F3](acceptance.md) 要求**滤波作用于全量数据**。若前端先聚合再滤波，滤波就是在聚合后的数据上做的，
**结果直接是错的**——不是慢，是错。因此 ①②③ 只能在后端，且顺序固定。

## 3. 契约是物理边界

分层不能只是编码约定。约定靠 AI 自觉遵守，而 AI 恰恰是问题来源。
因此契约落在**物理边界**上（进程边界 / 语言边界 / 通信边界），使违规**在结构上不可能**发生。

具体体现：

- 前端与后端是不同进程、不同语言，只能通过 JSON 消息说话。
- 数据源、滤波、聚合都在后端，前端物理上接触不到原始数据。
- 渲染器只拿到"绘制数据"，拿不到原始点。

## 4. 大数据显示策略

**原则：图表是用来发现问题的。绝不因为"屏幕上画不下"而丢弃数据点。**

> **等间隔抽样、均值抽样会抹掉尖峰与单点异常——而尖峰恰恰是要发现的问题本身。**
> **故禁止一切抽样手段。**

三层机制：

| 层 | 做什么 | 目的 |
| --- | --- | --- |
| **数据层** | 全量保留原始数据点，不做"为显示服务"的裁剪 | 结论不失真 |
| **视口层** | 只渲染当前可见范围 | 交互流畅 |
| **像素层** | 可见点数多于像素列数时，每列取该列内所有点的**最小值与最大值**，画成一条竖线段 | 有限像素上仍不丢失极值 |

**为什么 min/max 不丢尖峰**：尖峰就是它所在像素列的 max，必然被画出。
屏幕上看仍是完整波形，而不是"抽稀后的骨架"。
这是工业界处理大规模时序图的标准手段（音频波形、金融图表同理）。

**必须可见**：

1. 界面必须**标注当前是否处于聚合显示状态**。
2. 使用者必须能对任意区间**放大查看原始点**。
3. 聚合**可关闭**；关闭后若点数过多无法渲染，给出明确提示，而不是静默降级成抽样。
4. 滤波作用于全量数据，不受显示层影响。

## 5. UI 层约束

**目标：UI 可以随时重做，而不触碰核心与插件。**
起点允许是简单界面，但以下六条从第一天起就要成立。

| 编号 | 约束 | 为什么 |
| --- | --- | --- |
| **U1** | UI 层**不含业务逻辑**。只做两件事：把状态渲染出来；把用户操作转成命令发出去 | 界面里一旦出现"该不该显示""参数合不合法"这类判断，改 UI 就会碰到逻辑 |
| **U2** | UI 与核心之间**只有两类消息**：命令（UI→核心）、状态与事件（核心→UI） | 接口稳定 ⇔ 随便改界面都不用碰核心。**验收方法：新增一个界面面板，核心代码应零改动** |
| **U3** | 渲染器**接口**不依赖任何 UI 框架，只认「契约数据 + 一个挂载容器」 | 接口一旦绑框架，"渲染器可整块替换"就作废 |
| **U4** | 视觉相关的值（颜色、间距、字号）集中管理（CSS 变量） | 改风格只改一处 |
| **U5** | 界面结构与逻辑分离，不在逻辑代码里拼大段 HTML 字符串 | 调布局不碰逻辑 |
| **U6** | 前端可以使用带构建步骤的技术，但必须满足：① 开发期存在"改完即见"的热更新路径，**不需要手动执行构建命令**；② 构建只发生在交付环节 | 判据是**开发期体验**，不是技术形态 |

## 6. 插件机制

### 6.1 三类插件

| 插件类型 | 输入 → 输出 | 位置 |
| --- | --- | --- |
| **数据源** | 日志/数据流 → 契约数据 | `backend/sources/`、`plugins/sources/` |
| **滤波** | 全量数据 → 全量数据 | `backend/filters/`、`plugins/filters/` |
| **渲染** | 绘制数据 → 画布 | `frontend/renderers/`、`plugins/renderers/` |

### 6.2 数据源插件的两种模式

| 模式 | 输入 | 状态 |
| --- | --- | --- |
| **一次性** | 一个已存在的文件 | 本期实现 |
| **持续** | 串口 / 调试器 / 网络配置；挂载后持续产出数据块 | 预留接口，本期不实现 |

> **将来的实时数据更新 = 写一个"持续模式"的数据源插件。** 核心不需要改动，也不需要新增插件类别。

### 6.3 机制

- **目录即插件**：一个插件一个独立文件夹，可整目录增删。
- 每个插件含 **manifest**，声明：名称、类型、模式、版本、入口、参数、文案。
- 启动时扫描约定目录并注册；**无插件的空目录也是合法状态**。
- **异常隔离**：插件抛出的错误被捕获、记录并呈现，不向主流程传播。
- **无需编译**：接入插件不得要求构建步骤。

### 6.4 编排的界面要求

- 插件放入目录后，界面上应**自动出现**对应选项（热重载为加分项）。
- 滤波插件的参数控件由其**参数声明自动生成**。
- **不提供"必须编辑文本文件才能生效"的配置路径。** 配置文件可以存在（保存用户选择），但不得成为新增插件的必经步骤。
- **验收标准（[S5](acceptance.md)）**：从"文件放进目录"到"界面上能用"，中间不得有手工编辑文件或写代码的步骤。

---

## 7. 明确禁止

1. 禁止把新功能直接写进核心层。
2. 禁止一个文件承担多个环节的职责（数据源 + 绘图 + 滤波混写）。
3. 禁止插件之间互相直接调用；需要组合时通过契约或核心编排。
4. 禁止在插件中复制核心已有逻辑；公共能力上提到核心或公共工具库。
5. 禁止为内置功能保留第三方插件无法使用的特权接口。
6. 禁止任何形式的"为显示流畅而抽样"。
7. 禁止把存储格式写进接口名（见 [modules/storage.md](modules/storage.md)）。
8. 禁止在读写过程中丢弃契约不认识的字段（否则扩展区形同虚设）。
