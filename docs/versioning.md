# 版本号规则

> 本项目要求 **提交与版本号一一对应**。规则见 [AGENTS.md](../AGENTS.md)。

---

## 1. 有两个版本号，不要混

| | 位置 | 什么时候变 |
| --- | --- | --- |
| **应用版本** | 根目录 `VERSION` | **每次提交都变** |
| **契约版本** | 契约里的 `schema_version` | **只在数据结构发生破坏性变更时变** |

两者独立。契约新增一个可选字段 → 应用版本 `PATCH`/`MINOR` 递增，契约版本可能不动。
契约删字段、改语义 → 契约**主版本**必须递增，应用版本至少 `MINOR`。

---

## 2. 应用版本：语义化版本

格式 `MAJOR.MINOR.PATCH`，例如 `0.2.1`。

| 段 | 什么时候 +1 | 例子 |
| --- | --- | --- |
| `MAJOR` | 破坏性变更。**0.x 阶段不用**——按语义化版本的规定，0.x 阶段任何东西都可能变，破坏性变更由 `MINOR` 承担 | `1.0.0 → 2.0.0` |
| `MINOR` | 新增能力、契约新增字段、新增插件类型、架构调整 | `0.1.0 → 0.2.0` |
| `PATCH` | 修复、文档、工具、其它 | `0.1.0 → 0.1.1` |

递增到高位时，低位归零：`0.2.7` 升 `MINOR` → `0.3.0`。

---

## 3. 每次提交都要递增（硬规则）

**正常做法**：用脚本提交，它自动递增。

```powershell
python scripts/commit.py -m "修复: 修正示例中的 kind 名称"
python scripts/commit.py -m "新增: 存储格式探测" --bump=minor
python scripts/commit.py -m "交付 0.3.0" --tag --push
```

**直接 `git commit` 会被拒绝**——pre-commit 检查到 `VERSION` 未更新就中止。
这条检查存在的唯一目的，就是拦住"绕过脚本、忘了升版本"。

### 递增级别怎么定

脚本默认 `--bump=auto`，按改动内容推断：

| 改动内容 | 推断结果 |
| --- | --- |
| 动了 `contract/schema/` 或 `contract/examples/` | `minor`（契约变了） |
| `backend/`、`frontend/`、`plugins/` 下**新增**了文件 | `minor`（新能力） |
| 其它 | `patch` |

自动推断只是省事，**判断不准时显式指定**：`--bump=minor`。

---

## 4. 提交信息的格式

```
vX.Y.Z <中文描述>
```

例：`v0.2.0 新增: 落地契约 schema 与消息清单`

**版本号必须在最前面**。这样 `git log --oneline` 一眼就能看出演进过程。

---

## 5. 标签

- **交付时**打标签：`python scripts/commit.py -m "..." --tag`
- **日常提交不必打标签**——标签太密就失去"标记交付点"的意义

```powershell
git tag              # 看所有交付点
git show v0.3.0      # 看某个交付点的内容
```

---

## 6. 怎么查当前状态

```powershell
Get-Content VERSION    # 当前版本
git log --oneline      # 每次提交对应的版本
git tag                # 交付点
```

---

## 7. 为什么不用提交 hash 代替版本号

hash 唯一、精确，但**不可读、无顺序、不含"改动大小"的信息**。
版本号补的是这三点，另外它还能对应到打包出来的 exe——出问题时使用者报的是版本号，不是 hash。

两者并存：hash 管精确追溯，版本号管人话沟通。

## 8. 现状

`0.1.0` 是**版本号系统引入时的基线**。此前的提交没有版本号，不必追溯补写。
